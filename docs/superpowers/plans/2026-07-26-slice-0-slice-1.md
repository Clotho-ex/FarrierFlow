# Slice 0 and Slice 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers:subagent-driven-development` (recommended) or
> `superpowers:executing-plans` to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver Slice 0 Foundation followed by Slice 1 Connected Records,
ending with the complete client → service location → horse → barn appointment
flow verified after app relaunch.

**Architecture:** SwiftUI views render state and forward actions to
`@MainActor @Observable` feature models. Feature models own drafts and
coordinate `ModelContext` operations; actor-neutral draft, validation,
calendar, relocation, and deletion rules remain independently testable.
SwiftData V1 is a versioned local-only schema with explicit inverses and delete
rules. `FarrierFlowApp` supplies one concrete `ModelContainer` through
SwiftUI's model-container environment; no application dependency container,
repository layer, event bus, or service locator is introduced.

**Tech Stack:** Swift 6 with strict concurrency, SwiftUI, Observation,
SwiftData, Swift Testing, XCTest UI testing, iOS 18.0 minimum, latest stable
iOS 26 SDK.

## Global Constraints

- Read and follow `AGENTS.md`, `PRODUCT.md`, `DESIGN.md`, `ARCHITECTURE.md`,
  `DATA_MODEL.md`, and `ROADMAP.md` before each implementation session.
- The authorized sequence is Slice 0, then Slice 1. Do not begin Slice 1 until
  every Slice 0 exit criterion passes.
- Keep app, unit-test, and UI-test deployment targets at iOS 18.0 and device
  family at iPhone.
- Use the iOS 18 `Tab` API inside standard `TabView`, with one independent
  `NavigationStack` per tab.
- Use standard `List`, `Form`, `Section`, `Picker`, `DatePicker`,
  `ToolbarItem`, `Menu`, `sheet`, `alert`, `confirmationDialog`, and
  `ContentUnavailableView` behavior.
- Do not call iOS 26 visual-effect APIs. Standard controls must inherit the
  native iOS 18 and iOS 26 appearance without simulated Liquid Glass.
- Use `@State` for view-owned `@Observable` feature models, `@Bindable` only
  where a view needs bindings, and stable SwiftData identity in `ForEach` and
  routes.
- Keep user-facing strings localizable and format dates with locale-aware
  `FormatStyle` APIs.
- SwiftData is the local source of truth. Explicitly set
  `cloudKitDatabase: .none`; add no network, account, CloudKit, notification,
  StoreKit, photo, PDF, money, invoice, payment, visit, archive, or Settings
  code.
- Do not persist UUID fields, a Client–Barn relationship, profile photos,
  default service, historical-location fields, or any other field absent from
  `DATA_MODEL.md`.
- Do not stage, commit, push, or open a pull request unless the user separately
  requests it.
- Preserve unrelated worktree changes. The project uses file-system-synchronized
  Xcode groups, so source-file additions normally require no PBX file entries.
- Use the installed `iPhone 16 Pro` iOS 18.0 and `iPhone 17 Pro` iOS 26.5
  simulators. Do not create or clone simulator devices.

- [ ] **Step 3: Implement the versioned schema**

`FarrierFlowSchemaV1` is actor-neutral and conforms to `VersionedSchema`:

```swift
nonisolated enum FarrierFlowSchemaV1: VersionedSchema {
    static let versionIdentifier = Schema.Version(1, 0, 0)

    static var models: [any PersistentModel.Type] {
        [Client.self, Barn.self, Horse.self, Appointment.self, AppointmentHorse.self]
    }
}
```

Define each model as a nested `@Model` type in an extension of
`FarrierFlowSchemaV1`. `CurrentSchema.swift` provides top-level aliases to the
nested V1 types so feature code does not encode a migration version.

Use these exact stored properties and relationship annotations:

```swift
// Client
var name: String
var phone: String?
var email: String?
var notes: String?
@Relationship(deleteRule: .deny, inverse: \Horse.client)
var horses: [Horse] = []

// Barn
var name: String
var address: String?
var contactNotes: String?
@Relationship(deleteRule: .deny, inverse: \Horse.currentBarn)
var horses: [Horse] = []
@Relationship(deleteRule: .deny, inverse: \Appointment.barn)
var appointments: [Appointment] = []

// Horse
var name: String
var safetyNotes: String?
var appointmentIntervalWeeks: Int = 6
var client: Client
var currentBarn: Barn
@Relationship(deleteRule: .deny, inverse: \AppointmentHorse.horse)
var appointmentHorses: [AppointmentHorse] = []

// Appointment
var startDate: Date
var notes: String?
var expectedDurationMinutes: Int?
var barn: Barn
@Relationship(
    deleteRule: .cascade,
    minimumModelCount: 1,
    inverse: \AppointmentHorse.appointment
)
var appointmentHorses: [AppointmentHorse] = []

// AppointmentHorse
var appointment: Appointment
var horse: Horse
```

The required to-one properties use SwiftData's `.nullify` default on their
source side. Their inverse to-many relationships carry the explicit `.deny` or
`.cascade` rule. Do not put inverse annotations on both sides because mutually
expanding relationship macros are unnecessary. Do not add scalar fields to
`AppointmentHorse`. Keep `Item.swift` only until Task 6 replaces the running
app shell; do not register Item in V1.
